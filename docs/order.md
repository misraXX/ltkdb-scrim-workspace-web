# Codex指示：Scrim Workspace Web 改善Order追加・順次実装

## 前提

このリポジトリには、LTKDBの編集を補助する `Scrim Workspace Web` があります。

Scrim Workspace Web は、スクリム結果の画像アップロード、BP結果確認、画像認識結果の確認・修正・承認を補助する React/Vite アプリです。

現状の構成は以下です。

* フロント: React / Vite
* DB: Google スプレッドシート
* 画像保存: Google Drive
* 処理本体: GAS
* API仕様: `api-contract.md`
* 初回ロード: `workspace-bootstrap`
* 対象タブ:

  * 予定と試合ID発行
  * スクショ提出
  * 確認待ち

API共通仕様は以下です。

* GET: `?api=scrim-workspace&action=...`
* POST: JSON body
* response envelope: `{ ok, action, data?, error? }`
* `.env.local` の `VITE_GAS_MODE=gas` ならGAS実データ
* 未設定または `mock` ならmockデータ

## 注意

今回の目的は、いきなり一括実装することではありません。

まず Order にタスクを追加し、以下の順番で安全に進めてください。

重大な問題、仕様不明点、設計矛盾、API互換性リスクがある場合は、Codex側で勝手に判断して進めず、必ず ChatGPT に差し戻してください。

## 設計書チェック

1. README / api-contract.md / 実装内容と矛盾しないか
2. 既存APIのpayload / response envelopeと矛盾しないか

5. スプレッドシート構造の変更が必要か

7. 仕様変更が必要な場合、設計書更新が必要か

矛盾や不明点がある場合は、実装を止めて ChatGPT に差し戻してください。

## 目的

Scrim Workspace Web の作業効率を改善します。

特に最優先で改善したいのは、画面読み込み・再読込・確認待ちの次試合読込が遅すぎる問題です。

現状、毎回APIを叩いてスプレッドシートの最新情報を取得していることが原因の可能性があります。

そのため、以下のような改善を検討してください。

* 操作後に全体再取得しない
* 変更をローカルstateに反映する
* 必要な部分だけ再取得する
* まとめて更新できる処理はまとめる
* 確認待ち承認後にすぐ次の試合を見られるようにする
* ボタン二重押下による二重更新を防止する

# Order 2：不要な再読込の削減

## 実行条件

Order 1 の調査結果で、フロント側だけで安全に改善できる箇所が確認できた場合のみ実装してください。

重大な仕様不明点がある場合は実装せず、ChatGPTに差し戻してください。

## 目的

操作後の不要なAPI再取得を削減し、体感速度を改善します。

## 実装方針

以下の方針で実装してください。

* 初回のみ `workspace-bootstrap` を使う
* 操作後は必要なデータだけを再取得する
* 可能な場合はAPI再取得ではなくReactのローカルstateを更新する
* 無条件の全体再取得を避ける
* 成功した操作内容に応じてsummary件数をローカル更新する
* 整合性確認が必要な場合のみ、対象データだけ再取得する

## 例

承認成功後:

* `reviewList` から対象試合を削除
* 確認待ち件数を `-1`
* すぐに `workspace-bootstrap` 全体再取得はしない

スクショ提出成功後:

* 該当試合の提出状態だけ更新
* スクショ未提出件数を更新
* 全体再取得はしない

BP保存成功後:

* 該当試合のBP保存状態だけ更新
* 必要な場合のみ対象データを再取得する

## 禁止事項

以下は禁止です。

* 操作のたびに無条件で `workspace-bootstrap` を再実行する
* 保存や承認のたびに全タブ分のデータを再取得する
* API payload を勝手に変更する
* GAS側の仕様を勝手に変える
* スプレッドシート構造を変更する

## 成果物

報告には以下を含めてください。

* 実装内容
* 削減したAPI呼び出し
* まだ再取得が必要な箇所
* 変更ファイル
* 既存仕様との整合性
* 動作確認結果
* 残課題
* 次のOrderに進んでよいか

# Order 3：確認待ちの承認中並行チェック対応

## 目的

確認待ちで、承認処理中でも次の試合を確認できるようにしてください。

現在、確認待ちの試合を順番に承認していく際、次の試合の読み込みにも時間がかかり、作業ストレスが大きいです。

承認処理を待たずに、次の試合チェックを進められるUIに改善してください。

## 要件

以下を満たしてください。

* 承認ボタンを押したら、その試合だけ承認中にする
* 画面全体をロックしない
* 承認中でも別の試合を選択できる
* 承認中でも次の試合のチェックを進められる
* 承認完了後、対象試合を一覧から削除または承認済み表示にする
* 承認完了後、確認待ち件数を更新する
* 承認失敗時は一覧に残す
* 承認失敗時はエラー表示する
* 同じ試合の承認ボタンだけ二重押下できないようにする

## 状態管理案

以下のような状態管理を検討してください。

* `approvingMatchIds: Set<string>`
* `savingMatchIds: Set<string>`
* `loadingDetailMatchId: string | null`
* `selectedMatchId: string | null`

## 禁止事項

以下は禁止です。

* グローバルな `isLoading` で画面全体を止める
* 承認完了まで次の試合を選べなくする
* 承認後に毎回 `workspace-bootstrap` を全取得する
* 承認処理中に他の試合確認を妨げる

## 成果物

報告には以下を含めてください。

* 実装内容
* 確認待ちの操作フロー
* 承認中に別試合を確認できることの確認結果
* 変更ファイル
* 既存仕様との整合性
* 残課題
* 次のOrderに進んでよいか

# Order 4：予定と試合ID発行の BLUE/RED 選択UI改善

## 目的

`ScheduleTab.tsx` の BLUE / RED 選択欄を改善してください。

現状、BLUE と RED の選択欄がありますが、任意のチーム一覧から選ぶのではなく、その上段にある「左チーム」「右チーム」のどちらかを選ぶ方式にしたいです。

## 要件

以下を満たしてください。

* 左チーム、右チームの入力欄は維持する
* BLUE は「左チーム」または「右チーム」から選ぶ
* RED は「左チーム」または「右チーム」から選ぶ
* BLUE に左チームを選んだ場合、RED は右チームになる
* BLUE に右チームを選んだ場合、RED は左チームになる
* RED を変更した場合も BLUE が反対側になる
* BLUE と RED が同じチームにならない
* 左チーム / 右チームが未入力の場合は、未入力であることが分かる表示にする
* API payload は従来仕様と互換性を維持する

## 実装案

内部stateとして以下を検討してください。

* `leftTeam`
* `rightTeam`
* `blueSide: "left" | "right"`
* `redSide: "left" | "right"`

送信時に以下のように変換してください。

* `blueTeam = blueSide === "left" ? leftTeam : rightTeam`
* `redTeam = redSide === "left" ? leftTeam : rightTeam`

## 注意

`save-planned-match` のpayload互換性を壊さないでください。

## 成果物

報告には以下を含めてください。

* 実装内容
* 既存 `save-planned-match` payload との互換確認
* BLUE/RED が同一にならないことの確認
* 変更ファイル
* 動作確認結果

# Order 6：全ボタンの二重更新防止

## 目的

各ボタンを押して更新処理に入った場合、同じ処理を二重実行できないようにしてください。

## 対象

APIを叩くすべてのボタンを対象にしてください。

例:

* 新規予定作成
* 予定更新
* 試合ID発行 / 更新
* 画像送信
* BP保存
* 確認待ちの編集保存
* 確認待ちの承認
* 一覧更新
* 詳細読込
* その他APIを叩くボタン

## 要件

以下を満たしてください。

* ボタン押下後、該当処理が完了するまでそのボタンをdisabledにする
* 処理中であることが分かる文言に変える
* 成功 / 失敗後にdisabledを解除する
* エラー時も必ず `finally` で解除する
* 確認待ちの承認は画面全体をdisabledにしない
* 確認待ちの承認は、該当matchIdの承認ボタンだけdisabledにする
* 他の試合選択や確認作業は継続できるようにする

## 文言例

* 保存
* 保存中...
* 承認
* 承認中...
* 送信
* 送信中...
* 読込
* 読込中...

# 重大な問題がある場合の差し戻しルール

以下のいずれかに該当する場合は、実装を止めて ChatGPT に差し戻してください。

* 既存APIのpayloadを変更しないと実現できない
